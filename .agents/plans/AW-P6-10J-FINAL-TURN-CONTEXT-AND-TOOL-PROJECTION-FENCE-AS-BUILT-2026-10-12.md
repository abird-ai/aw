## 3. Minimal implementation — same original run receipt projection, no new ledger

Only production source `crates/aw-store/src/journal.rs` is modified. Its existing private `OriginalRunReceipts` derived from the ONE immutable `run_events` reader now also retains the factual ordered original `JournalEntry::Assistant` messages (the same records it already used for bounded assistant text). New private `validate_original_context_projection(&Turn,&OriginalRunReceipts)` is invoked inside the SAME `BEGIN IMMEDIATE` final-result transaction **before final node insert, paid attempt settlement or branch attachment**. Existing normal finalization and crash recovery both use this one projection, with the original `ORDER BY seq LIMIT 513` / explicit 512-event maximum; no extra SQLite query, index, table, journal or provider invocation.

The validation enforces these deliberately small and nonwidening rules:

- An explicitly retained context trace begins with the **original User prompt** and original `turn.id * 1024` message ID, without Tool/Assistant-only fields or provider-private continuation. No subsequent `Role::System` or another `Role::User` can be invented to impersonate higher trust. The original Agent generates exactly this initial User message, and no provider or extension decides the System role.
- Each context `Role::Assistant` must be a **byte-equivalent typed message from the actual immutable Assistant journal**, including original ToolCall name/ID/arguments and text. A **Completed** Turn must retain the full exact original order; an interrupted/failed Turn may retain only a factual **ordered subsequence** (an Assistant event can be persisted before the same Turn's projection is appended). No fabricated Assistant proposal or skipped original ToolCall can become next-model context. `provider_context` stays excluded from serialization and is never restored as a grant.
- Each context `Role::Tool` message needs the **actual original ToolRecord** (same call ID and name, a factual `ToolFinished` Succeeded/Failed or `ToolDenied`, nonempty original result). A merely proposed ToolCall or unfinished `ToolStarted` does not qualify. The earlier `aw_agent_core::validate_messages` still enforces proper proposal/results ordering and prevents orphan/duplicate batch messages for completed history.
- Critically **do not compare `Role::Tool.content` to immutable `ToolOutput.content`**: the original typed, host-controlled Tool-output Hook may legitimately redact or change **model-visible presentation text** without changing the factual result or minting another receipt. Do not compare arbitrary streamed `Turn.answer` with Assistant body either; partial streams, failed output gates and observational text are NOT immutable external effect receipts. The final Tool/paid records themselves retain AW-P6-10I's exact original immutable-output/identity/usage comparisons.
- A historical empty context trace is still allowed, including old Store clients and owner-crash recovery; failed/cancelled traces can be partial but cannot add invented roles, Assistant messages or Tool result authority. No automatic paid replay or source permission follows from a message, Tool ID or Hook projection.
