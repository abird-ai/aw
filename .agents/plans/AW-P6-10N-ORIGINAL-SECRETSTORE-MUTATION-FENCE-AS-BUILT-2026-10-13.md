## 2. Actual native negative-first reproduction and exact minimal fix

**Before source change:** Changed the original test-only AW-P6-10M observation into `aw_p6_10n_maintenance_lease_fences_every_existing_direct_secretstore_handle` in the same original `crates/aw-store/tests/composite_design.rs` test target. It opened the real persistent owner Store, cached TWO independent original vault handles before maintenance, stored one real private ciphertext, acquired the actual original `backup` lease, and asserted both a new `put` and deletion of original item were **DENIED** while read-only `get` remained available. The **FIRST denial assertion FAILED against live pre-N code**: vault mutation was accepted despite a valid original maintenance lease. The earlier M observation remains correct *for its historical source*, but its native test has now been superseded by a positive N regression; do not pretend the old failing M predicate is still the current correct product contract.

**Single existing vault, one stable file lock:** `crates/aw-store/src/secret_store.rs` now defines a private owner-only stable advisory lock file at `secrets/.mutation.lock`, outside the encrypted `items/` directory. The existing `aw_platform::ensure_private_dir` plus `open_private_rw_create` enforce original Unix 0700 directory, 0600 owner-only single-link regular file, `O_NOFOLLOW` and no replacement of an existing lock inode. Every real `LocalSecretStore::put` and `delete` (including cached and independently reopened vault handles) obtains a NEW **shared** OS `fs2::FileExt::try_lock_shared` for the entire write-once encrypted-file creation/fsync or removal/fsync. The Fd is dropped at the end of that exact operation. Read-only `get/exists` remain permitted during maintenance; successful/failed write and delete return existing `Result` errors and create no new SQL authority. A fresh vault `master.key` creation is ALSO a mutation: on a missing master, `LocalSecretStore::open` obtains an **exclusive** lock on the same stable file, re-reads the master under that lock to avoid simultaneous initializer races, then applies existing missing-items fail-closed logic or creates the same original 32-byte private master once. An existing master may be loaded read-only under an active backup cut. Existing file encryption uses the SAME original ChaCha20-Poly1305 AAD, nonce and opaque `sec_` ref format.

**One original owner maintenance lifetime:** `crates/aw-store/src/lib.rs` adds one private, nonserialized `Inner::vault_maintenance` slot in the already shared `Arc<Inner>`, holding **the exact original `LocalMaintenanceLease` token and an exclusive owner-only file descriptor**. On `SessionStore::acquire_local_maintenance_lease` the caller's existing original coordinated Process identity is checked, the slot must be vacant, then the original stable SecretStore lock is acquired **EXCLUSIVELY and nonblockingly BEFORE** admitting the existing SQLite `coordination::acquire_maintenance` transaction. A real in-flight vault writer holding shared file lock makes snapshot admission fail immediately with Conflict; no new SQL maintenance lease is committed and no partial SQLite backup is published. The original SQL maintenance admit can still independently fail for active/hazardous effects, and dropping the file descriptor on error returns the OS gate to normal. A successful lease retains the exclusive OS lock in original `SessionStore` shared ownership until release; a clone cannot bypass it. Release matches the EXACT immutable lease identity/process/generation and commits the original SQL release **before** dropping the exclusive file lock. A stale or altered lease does NOT unlock the vault or settle SQL maintenance. OS process termination automatically releases the advisory lock even without Rust destructors. No extra background worker, database row, long-lived transaction or second owner lock is created.

**Original restore-generation special case:** `SessionStore::restore_backup` uses the existing SQLite backup API to make a staged copied image live while changing `restore_generation`, fencing the old original process, and resetting its prior SQLite maintenance lease to IDLE in the restored image. Thus an ordinary `release_local_maintenance_lease(old_token)` after successful restore would correctly fail against the newly installed Process identity. The production restore success path now explicitly checks and drops only the corresponding **old OS vault file fence after** installing the newly fenced authoritative Process identity. Failed staging/copy attempts still release the original SQL and vault maintenance lock together through the existing failure path. This is an essential liveness/correctness boundary: it cannot leave all future vault mutations blocked after legitimate operator restore, or unlock a false maintenance lease before the original SQL generation transition commits.
