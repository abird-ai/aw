## 2. Reproduced real bug A: partial portable export left behind after a file write error

Existing `SessionStore::export_file(actor,session,path)` first calls original `export_jsonl` for complete owner-only release authorization and bounded data, then calls Unix `private_new(path)` (exclusive, O_NOFOLLOW, single-link, owner-validated `0600`) and `write_all`; only `sync_all` follows. A host filesystem write returning an error after the file was created left **an owner-facing truncated, sensitive JSONL artifact at that path**, incorrectly appearing like a usable export and unnecessarily retaining partial private data. A preexisting file or symlink is correctly rejected by exclusive create and must NEVER be removed; unauthorized export must create no artifact.

**Negative-first real native Linux failure:** `aw_p6_10l_portable_export_partial_write_failure_removes_only_new_file` creates a real original SessionStore and bounded session-tree JSONL larger than 1 KiB in a dedicated test child, uses `prlimit` to lower **only that child's** RLIMIT_FSIZE to 1024 bytes AFTER Session creation, and uses a child Bash `SIGXFSZ` ignore to receive actual kernel `EFBIG` (`FileTooLarge`) rather than kill the process. This exercises the real public `export_file`, actual `private_new`, real partial `File::write_all`, and original private filesystem; the main test process' file limits/signals stay unchanged. Initial test harness applied the limit too early and hit SQLite WAL I/O instead; that incomplete test was **not counted as reproduction**. Corrected in-memory ledger fixture isolates the actual on-disk export writer. The new assertion **FAILED BEFORE fix** with `Err(FileTooLarge)` and `exists=true` (real truncated JSONL file). After the production fix it PASSED with the same real error and no leftover partial file. No synthetic error injection or alternate export method is used. Requires Linux native `prlimit`/Bash and a private temp directory; this is not claimed as a native Windows/macOS fault-injection gate.

**Bounded fix, only `crates/aw-store/src/archive.rs`:** The original full export authorization and bytes remain computed **before** an exclusive file create, preserving fail-before-create for unauthorized/oversized/incomplete Sessions. Once `private_new` succeeds, run the original `write_all`, `File::sync_all()` and newly explicit `aw_platform::sync_parent(path)` as one success/failure block; close the newly owned writer before returning and remove **only its own created** partial artifact on any write/fsync error. `private_new` returning an error immediately exits without cleanup, so an existing backup, preexisting owner-owned export, symlink, or unrelated file is never unlinked. This remains an owner-authorized `0600` **plaintext** export, not a new auto-encrypt/auto-scrub service, a guarantee against malicious same-UID race/path replacement, or a natural-power-loss/remote-filesystem atomicity certification.

`aw_p6_10l_portable_export_rejects_existing_paths_without_touching_bytes` separately PASSES with real existing 0600 owner JSONL bytes, repeated exclusive-create attempt, existing symlink, and unauthorized principal. It confirms no overwritten/destroyed data or orphan file is produced by rejected owner/export permission. The existing original `export_round_trip_is_new_history_not_new_billing` PASSES and still creates a new Session without importing original paid vendor receipts/grants; no automatic provider/Tool execution or false billing.

## 3. Reproduced real bug B: SQLite-only restore silently generated a NEW unrelated SecretStore key

Original `SessionStore::backup` makes a WAL-aware, `0600` SQLite-only `VACUUM INTO` snapshot. Encrypted queued Input payloads, extension Secret settings and provider/OIDC/OAuth credential blobs live in separately owned SecretStore `secrets/master.key` and write-once `secrets/items/sec_*.bin` **outside the SQLite backup**. SQLite v33 retains immutable original encrypted payload references in `audit` and provider/auth metadata, NOT ciphertext/key bytes. Original `LocalSecretStore::open` already rejects a missing master when *encrypted item files are still present*, but if both the original master and encrypted items are absent—as in a genuine SQLite-only snapshot copied to a fresh private state directory—it silently creates a brand-new key and returns a supposedly usable vault, while the SQLite references cannot be decoded.

**Negative-first actual SQLite/SecretStore restore:** `aw_p6_10l_sqlite_only_restore_does_not_silently_mint_a_replacement_secret_master` creates a real on-disk original Session/branch/WriterEpoch, stores a bounded queued Input under an actual encrypted write-once secret ref, produces a real WAL-consistent SQLite backup and closes the original owner. It copies ONLY `sessions.sqlite3` into a separate `0700` owner state root and reopens `SessionStore`. The new assertion **FAILED BEFORE fix**, because `local_secret_store()` returned success and created a fresh unrelated master key. The fix makes that exact case **fail closed before key creation**, retaining the original immutable SQLite refs for operator inspection rather than silently turning them into unusable custody or replaying the queued input.

**Bounded production fix, only `crates/aw-store/src/secret_store.rs::SessionStore::local_secret_store`:** When `secrets/master.key` is absent, one READ-ONLY existing-v33 SQLite `SELECT EXISTS` probe checks whether original immutable `audit` has any encrypted Actor Queue or Extension Secret custody, or provider/server-secret, OIDC provider, OAuth client secret or OAuth token-version tables record independent private-file credential refs. If so, return `Denied` with an actionable missing matching master-key/items restoration diagnostic **before** `LocalSecretStore::open` can mint a replacement key. If no such prior custody was recorded, normal first-ever SecretStore key creation remains allowed. With a master already present, the ordinary SecretStore path/AEAD validation remains unchanged: **no extra SQL scan on normal vault access**. The audit check is deliberately conservative: even historically removed queue/extension/credential items signal that a prior key/identity existed; automatic silent rekeying is not safe, and a deliberate operator rotation/recovery would need separately authorized custody work. No schema/migration, new key format, backfilled reference, or new cross-owner read permission.

The same test also executes three **positive and fail-closed real restoration cases**: a separately assembled matching original SQLite snapshot + original 0600 SecretStore master + correct encrypted item returns the EXACT original payload; a key-only restoration with the encrypted item missing returns a retrieval error and never invents the body; and a restored ciphertext under a synthetic WRONG master fails original CHACHA20-POLY1305 AEAD authentication, never returning plaintext. These are native controlled **manual directory-copy fixtures**, not a new product-supported single-command full-state backup or a proof that `restore_backup` automatically bundles files. Original `SessionStore::local_secret_store` is the checked Host API; directly bypassing it by invoking lower-level `LocalSecretStore::open` separately is not an authenticated linked-SQLite restore workflow.
