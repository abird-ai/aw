### 2B. Shared original Process-generation fence + explicit NO-writer cold quarantine

The prior ONLINE original `coordination::prepare_restore_snapshot` already advances `store_meta.restore_generation`, marks old active `local_process_incarnations` as **fenced**, converts active execution leases to durable **hazard** states (never retry), releases old write leases and resets old SQL maintenance. ### 2C. QUARANTINE that literally forbids normal owner/direct opening

The copied State has a private `0600` marker file **`.aw-cold-restore-pending`** with expected original store ID, source generation and newly fenced generation; this data is an internal **DENIAL marker**, never a bearer token or permission. The previously ordinary `SessionStore::open` and `SessionStore::open_trusted_local_direct` now call one small `reject_unapproved_cold_restore` immediately after validating/canonicalizing the original private State directory and **BEFORE** `owner.lock`, SQLite creation/migration, original Process registration, recovery, model/Tool/Queue paths or any provider client. An existing marker is a hard error—even a symlink or damaged marker cannot authorize opening. The marker is NOT automatically removed or accepted as an operator approval in S, and there is NO public activation method or hidden override flag. This protects against accidental normal application startup that would otherwise register a fresh owner Process and potentially process copied external-effect state. The explicit quarantine is stricter than silently copying an executable State and relying on undocumented assumptions about post-restore app startup.

The new private `verify_cold_quarantined_state(root, original_v1_manifest, new_generation)` reads ONLY copied files and copied v33 SQLite.
