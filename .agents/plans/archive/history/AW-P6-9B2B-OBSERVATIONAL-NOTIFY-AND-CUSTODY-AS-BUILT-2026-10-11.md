## 1. Design and hard boundaries

1. **Only Runtime, Actor, Message, Envelope** are primitives; Next and Defer remain the only hook verbs. This wave implements a *derived, authenticated, observational Notify service* using the original `aw-agent-core::runtime::HostRuntime`, `AgentSessionController` and `aw-agent-kernel::message::{ActorMessage,Kind::Notify}`. Notify never becomes Input, executable Control, Hook continuation, Agent Turn, provider billing or external-effect receipt. Typed `ActorOperation` requests are host-only; deserializing them does not authenticate RPC. External R12 Actor methods remain deliberately refused.
2. **Authoritative boundaries:** The existing current Session owner + SQLite Workspace writer epoch + current owning ActorKey generation, original child-parent relation, destination site, recipient branch and current Envelope are required before Runtime admission. A message from a stale, forged, unrelated, self-sender or released Actor cannot create a true `Accepted`. Only `Delivery::Queued` from the same original Runtime mailbox is treated as Notify acceptance. An absent/ambiguous send is `Unknown` with explicit inspection; never re-send to make an old message look delivered. `Kind::Hook` is forbidden; durable async Defer/Control execution is NOT added. A terminal child may send its final **data-only** status before it is released, using existing normal Actor rules.
3. **Durable custody with immutable receipts:** A bounded private UTF-8 body (1..65,536 bytes) is encrypted with the existing `LocalSecretStore` ChaCha20-Poly1305/0600 write-once blob, then an immutable `actor.notice` SQLite audit `Prepared` fact is appended under `BEGIN IMMEDIATE`, before attempting volatile Runtime send. The current same **process identity + store generation** and writer epoch must CAS `Prepared → Accepted` only after an actual Runtime `Delivery::Queued` receipt; a restarted owner cannot claim its predecessor delivered. Outcomes `Rejected` or `Unknown` never grant delivery or re-execution. Every state transition is append-only; original Session/Turn/run/tool/hazard evidence remains the only execution authority. Notice bodies, opaque `payload_ref`, plaintext SHA, and owner-process incarnation are **never included** in `ActorOperationResult` public `ActorNoticeView`.
4. **Owner observation / recovery:** A current authenticated Session writer may query/list redacted metadata and independently read decrypted **Accepted** private text with SHA-256 verification, including after process restart or a new parent Actor generation at the *same bound Session/branch/site*. This **does not re-inject** an old child Actor into the mailbox, resurrect sender keys, replay a tool/model call or itself establish user acknowledgment. A separate exact `Accepted` revision-CAS `AckNotice` commits `Read` then unlinks the private encrypted body; the original immutable accepted fact remains inspectable. A `Prepared` or `Unknown` body cannot be read as delivered; `InspectNotice` is explicit, terminal and note-bounded/printable and never makes it Accepted. Current `poll_notice_inbox()` uses the original Runtime mailbox, then verifies exact immutable Accepted sender+recipient generations, source sequence/ID, branch/site, Turn target, priority and payload SHA. Missing matching receipt poisons the owner instead of manufacturing a Notice ACK.
5. **Backpressure / ordering / collision:** At most 32 live `Prepared | Accepted | Unknown` notice facts per Session/branch/site, no silent eviction; 8192 immutable facts per Session with reserved room for accepted/outcome and terminal ACK/inspection. Global monotonic per-sender sequence/request-ID collision fences cross **9A Input, 9B1 Control, 9B2A Queue, 9B2B Notify**; all checks occur under the SQLite immediate write transaction. `qi_` stays reserved exclusively for deterministic 9B2A claim correlation. There is no fake total order between independent senders or fairness promise for immediate notifications: the single original bounded Runtime mailbox retains its existing semantics. A full runtime inbox cannot become falsely Accepted.
6. **Retired encrypted custody maintenance:** New `actor_reclaim_retired_custody` is a bounded (1..128) trusted-owner operation under the same Session current-writer CAS/SQLite `BEGIN IMMEDIATE`. It proves every candidate from the immutable historical `actor.queue`/`actor.notice` audit event references, calculates the **current live** queue and notice references, and unlinks **only** ledger-known refs provably retired by latest `Deleted/Settled/Inspected/Read/Rejected` states or earlier immutable queue edits. It writes append-only `actor.custody` outcomes (max 8192) and is idempotent across owner restart. Already absent files are recorded distinctly. Private SecretStore unlink calls `sync_parent`, but that is not secure overwrite/forensic erasure. **Never enumerate/delete an unreferenced file**: an orphan write before SQLite `Prepared`, a provider credential, OAuth token or unknown encrypted item has no proof it belongs to this queue. They remain for a separately designed owner-confirmed quarantine/retention procedure. Encryption key-loss, file-permission/symlink violations and malformed audit fail closed.
7. **Control/Hook decisions:** Do **not** persist a replayable Control or Hook continuation in this wave. Existing 9B1 Control `Prepared/Applied/Unknown` facts and owned async `Defer` one-shot generation/epoch/liveness rules remain sole authority. A started/stale/unknown Control is never interpreted as an Input or retried. `actor.notice` is an observation of an Actor child, not a command; provenance metadata is not an approval, grant, tool-result or user-facing security attestation.
