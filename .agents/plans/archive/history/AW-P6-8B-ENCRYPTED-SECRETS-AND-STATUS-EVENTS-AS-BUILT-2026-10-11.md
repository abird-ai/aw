## 1. Invariants and trust decisions

1. **Exactly four primitives** — Runtime, Actor, Message, Envelope — and exactly **two Hook verbs** — Next and Defer. Every change is a derived typed service. The original single Agent, ToolPolicy, TurnMachine, immutable journal, SQLite **v33**, JSONL **v1**, and existing `LocalSecretStore` remain the authority. No new model executor, durable bus, effect runner, browser privilege, file indexing/LSP, voice capture, tool grant, model payment or background daemon has been introduced.
2. **Private encrypted custody, not plaintext config:** `crates/aw-store/src/extension_secret.rs` defines `SecretSettingScope` bound to exact existing `Session ID`, **canonical** `Branch ID`, execution site, extension ID, setting name and active Workspace writer epoch. `SessionStore::{extension_secret_set,extension_secret_read,extension_secret_reset,extension_secret_view,extension_secret_list,extension_secret_reclaim_retired}` operate on existing SQLite `audit` action `extension.secret`, with current owning `PrincipalId`, writer epoch/state, branch and site checked separately on every call. The encrypted write-once bytes live in the **existing** ChaCha20-Poly1305 `LocalSecretStore` under an OS-random `sec_...` ref, synced to disk before the immutable `Active` metadata fact is committed. Only this fact may activate a blob; an unreferenced blob from a pre-commit crash is **not** an executable/readable setting. Replaced/removed refs are unlinked after a successfully committed new fact; a failed unlink yields explicit uncertainty, never fabricated erasure. SQLite audit may contain the private blob reference (owner metadata), never plaintext body. No `secret` key is added to ordinary user TOML, project resources, general R12 or a model-visible tool.
3. **Typed, registered, actively verified host owner only:** `aw::extension_secrets` is compiled only under existing `durable`. It accepts the existing 9C `aw::actor_owner::Service` and current 8A `SettingsRegistry`, verifies **original live Runtime Actor generation, current Envelope, actual owner/Session/WriterEpoch** using `verify_rpc_state`, and requires an explicitly registered `SettingKind::Secret{max_bytes}` from the trusted extension manifest for each operation. A client-provided extension name, site, ActorKey, epoch or maximum never supplies permission by itself. The host chooses active `SecretSettingScope` from the original bound Service, not RPC JSON. No secret RPC/web/CLI/network method is advertised. The literal plaintext `read` result is `Zeroizing<Vec<u8>>` and has no `Serialize` or `Debug`; queries/views/lists only expose `{extension,name,state,revision,configured}`. Original 8A ordinary `SettingsRegistry::resolve` still intentionally hides secret values. Session permissions are **not** general global profile credential grants.
4. **Strict CAS and recovery:** `Set` accepts exactly `expected_revision=None` for first use or the full previously seen positive revision; `Reset` requires an active value and exact revision. Immutable audit facts use `Active / Removed` and increment revision, never silently revive a removed item. Limits: 1–2048 secret bytes (further restricted to the trusted registered maximum), up to 64 active settings per Session, up to 4096 audit facts with 64 closure slots reserved, max 64 retired blobs processed per custody sweep. `reclaim_retired` derives candidate refs **only** from the exact Session/branch/site's immutable ledger, protects **every** live ref in that Session, tests for existing files before unlinking, and audits redacted sweep count. It leaves unrelated provider credentials, unreferenced ciphertext, suspected pre-ledger power-failure orphans and other principals' files alone. A sweep cannot certify physical forensic overwrite or a fully power-fail-safe encrypted storage subsystem.
5. **Status protocol v2 without a shadow event engine:** the original presentation-only `aw-ui-extension` registry accepts manifest **v1** only for original Slots, and v2 for `LeftStatus`, `RightStatus`, `BelowStatus`, `AfterStep`, `AfterFinalOutput`, alongside existing `AboveComposer`, `BelowComposer`, `FullscreenStatus`, `AfterTurn`. It preserves `UiExtension::project` and adds a default-noop `event(&EventContext)` method; no default plugin executes externally. New `Request::Event`/`Response::Event` are strictly typed and v2-only. `StatusSurface` derives six semantic status regions from the **same Registry** and increments local `StatusSnapshot.version` only when its bounded lines actually change; it does not create another persisted event stream. `EventRail` holds at most 32 **ephemeral** UI notices per exact Session, with positive, monotonically increasing sequence and at most 8 lines per event, deterministic priority and extension-ID ordering. Clearing UI presentation does **not** reset anti-replay sequence, and restarting an app never resurrects an event or re-injects anything into the original Agent journal. `StepEnd`, `TurnEnd`, `FinalOutput` are UI event labels, **not** new Runtime Message kinds, model results, Hook verbs or evidence of external paid effects.
6. **Original event source, metadata-only:** `aw::extension_status::factual_event_contexts` converts original `AgentEvent::InvocationFinished` to StepEnd and `AgentEvent::Finished` to TurnEnd; it announces FinalOutput only for original `Outcome::Completed` with nonempty assistant answer. Original raw `Turn.prompt`, `Turn.answer`, tool payloads and provider-private continuations are **never passed** to v2 event metadata or EventRail. Started, Delta, ToolStarted, Rejected and incomplete/cancelled/unknown Turns do not fabricate a success notice. Original authenticated Agent/provider/ToolPolicy and journal remain the actual source of factual status. v2 `EventContext` validates exact Session IDs, turn/sequence and bounds every public context metadata field; semantic event spans reject embedded terminal control or bidi overrides and obey existing line/span/byte ceilings. This is an **opt-in host API** for event notices, not an auto-enabled browser/web assistant-output channel.
7. **Actual opt-in native Workspace projection, default unchanged:** existing `aw::config::UiConfig.status_lines` now accepts persistent `LeftStatus`, `RightStatus`, `BelowStatus` regions via its **original atomic config lock and per-field CAS**, not a new config object/schema. Existing native `src/tui/extensions.rs` `StatusLineExtension` v2 uses the **same typed `project_status`** and semantic spans; user-chosen Session titles/path text are sanitized using the original `presentation::safe_text`, literal-escaping terminal and bidi controls, removing newlines/tabs and bounding span length. Existing `src/workspace/ui/render.rs` allocates side rows **only** for explicitly configured regions and sufficient terminal width; default has **zero extra header/footer/sidebar**. Narrow widths preserve the existing workspace panes; configured below-status adds at most 2 rows, side panes are bounded at 16–24 cols. Existing `FullscreenStatus` remains the original status renderer and layout. No UX plan or screenshot files were touched. New EventRail is *host-available and tested*, but there is no default installed v2 event listener or persisted notice history; renderer adoption beyond the opt-in host remains subsequent 8C/product UI wiring.
