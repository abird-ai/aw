## 1. Normative identity, media and privacy design

1. **Still exactly four primitives**: `Runtime`, `Actor`, `Message`, `Envelope`; still **only two Hook verbs** `Next` and `Defer`, one existing `Agent`, `TurnMachine`, `ToolPolicy`, original Session journal, SQLite v33 and JSONL v1, and no parallel process/extension/approval executor. Media typing is a property of the *original* `ActorMessage` (not a fifth primitive), and the framed port is a typed hosted **service** over the already-reviewed original `aw-tools::process::PipeProcess`. Actual media recording/playback is **NOT** enabled or certified.
2. **Portable no_std content-type seam**: `aw-agent-kernel::message::ContentType` is a pure `Text` (default) / `Image` / `Audio` / `Video` / `Binary` enum and `ActorMessage.content_type` is part of the original Rust SDK structure. All current internal original kernel, Runtime, Control, Hook, child and host message producers now explicitly use `ContentType::Text`; the original mailbox checks `content_type.text_only()` before reserving a source sequence or delivering to a text-only Agent/Hook/tool/provider. Any nontext type is hard-denied as `InvalidKind` with **no** new tool grant, effect, source sequence consumption, opaque media re-injection or implicit text coercion. Tests cover all nontext kinds and confirm the same sender can still submit the first proper text Message after a rejected nontext candidate. This is a Rust public struct source-shape addition; third-party Rust code creating literal `ActorMessage` values must explicitly supply the `content_type` field. It is **not** a change to the original E5 C ABI, JSONL, SQLite or persisted wire schema, and there is no dual legacy mode.
3. **Bidirectional data frames on the existing Process ONLY**: new `aw-tools::media_port::{FrameKind,Frame,FramePort}` is an ephemeral borrowed adapter to an **already independently authorized, already original-journaled** `PipeProcess`. It does NOT choose/spawn its own executable or root, bypass `ToolPolicy`, infer a source grant from frame content, enable an MCP/web/stdio/remote shell, or introduce another Process lifetime owner. Frames have one big-endian 4-byte byte-length, one kind byte, and 1–4096 bytes of data. Plain `Text` must be valid UTF-8; `Binary` and inert `Image` are permitted **only as opaque data** to a preauthorized Process. 1024 lifetime frames maximum, original Process bounded 48KiB contiguous head capture, no raw pipe tail/head concatenation, no automatic send retry after a partial/uncertain write, and no false Process/provider ACK. All incomplete, malformed, zero/oversize, unknown-kind and truncated/EOF frame states fail closed for inspection. A native Unix test uses an actual `cat` executable resolved from NixOS `PATH` and the original Process spawn, stdin, stdout drain/exit and bounded framing; no device, camera or live provider is launched.
4. **Privacy and consent, hard off boundary**: `FrameKind::Microphone`, `Speaker`, and `VideoCapture` **always** refuse encoding/decoding/writes in this slice, even with a forged frame or a caller-provided `consent` field. The Process module contains **no** media-device acquisition, recording/playback, live ASR/TTS, remote voice stream or outbound media provider selection. Current Process head/tail output is an ephemeral original memory capture, not a consented recording vault. Prior to enabling any real voice/audio path, a *separately reviewed implementation* must prove positive owner/user and Session-bound capture+playback consent (and revocation), OS device permissions and isolation, process sandboxing/source attribution, bounded/transparently disclosed retention and secure deletion, private audio custody, end-to-end backend TLS and authentication, stream interruption/unknown-effect recovery, no raw voice material in transcripts/UI/public logs, production privacy testing and real device/provider validation. None is implied by an inert content type or binary PipeProcess adapter. Do **not** claim audio privacy, TLS or user-consent certification in 8C.

The typed UI cannot make a guardian verdict into a Process capability or unjournaled Tool approval. `decide` requires an *explicit* reviewed exact 64-hex SHA256 and affirmative/negative decision from the current original owner before invoking the **same** transactional `SessionStore::review_decide_human` (only previously `waiting_human`, matching initiating user and still `waiting`, atomic compare/transition); human approval alone does **not** release source evidence.
