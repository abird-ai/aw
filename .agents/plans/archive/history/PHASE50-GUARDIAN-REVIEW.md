# Phase 50 — governed guardian review and explicit approval gates

Status: authorized 2026-10-06 by the user after Phase 49 review.

## Boundary

Phase 50 adds an optional **guardian review gate** over already verified Phase-46 team joins and Phase-49 planner joins.

The gate is a separate restricted model decision. It may block or require human approval, but it never grants provider, account, tool, root, worktree, budget, routing, scheduling, merge, or disclosure authority that was not already present.

SQLite advances to v32.

Phase 50 does not add inter-agent result messaging, parallel DAG execution, separate synthesis models, schedules/autonomy, trusted child shell, automatic Git import/merge, monetary budgets, or cross-machine child placement.

## Host opt-in

Guardian review requires the existing `--subagents` opt-in plus:

- `--subagent-guardian-route ROUTE`
- optional `--subagent-guardian-route-revision REV`
- `--subagent-guardian-policy TEXT`

The selected routing strategy must be:

- actor-owned;
- immutable;
- active;
- `role=guardian`;
- `mode=fixed`.

Guardian target selection is host-declared and inference-free. The guardian cannot select its own provider/account/model/endpoint.

At least one reviewed source tool must also be enabled: a bounded team and/or governed planner.

## Reviewed sources

Phase 50 gates only:

- a completed Phase-46 team join; or
- a completed Phase-49 planner join.

The team/planner join is still assembled and verified first. Full child answers remain authoritative only in child Sessions. Team/planner join tables continue to store provenance/digests, not full answer bodies.

Without a configured guardian, Phase-46/49 behavior is unchanged.

With a configured guardian, joined evidence is quarantined from the parent Agent until the guardian gate releases it.

## Review evidence

The guardian receives bounded typed JSON containing:

- source kind: `team` or `planner`;
- root objective;
- host-authored policy text;
- exact bounded joined evidence;
- exact joined SHA-256.

The joined evidence is untrusted candidate evidence, never instructions or authority.

The host policy is bounded and fixed for the run. It is not generated by the working model.

## Strict guardian verdict

Guardian output is strict JSON:

- `decision`: `pass | deny | needs_human | require_evidence`;
- `reason_code`: bounded token;
- `summary`: bounded explanatory text.

Unknown fields, malformed JSON, invalid decisions, oversized output, invalid reason codes, or incomplete provider replies fail closed.

Decision semantics:

- `pass` — the policy gate may release the already-authorized joined evidence;
- `deny` — block release;
- `needs_human` — create a durable explicit human approval request; no evidence is released yet;
- `require_evidence` — block release and require a later explicit rerun/review with more evidence; Phase 50 does not invent peer messaging or automatically solicit extra child work.

A `pass` can satisfy only this review requirement. It cannot override missing capabilities, expired/revoked provider grants, destination mismatch, root budgets, tool restrictions, explicit denials, Session access rules, or any other authority check.

## Tool-free guardian invocation

`aw-agent-core` exposes a dedicated `ReviewExecutor / ReviewJournal` path.

Guardian invocation:

- has no tools;
- appends no conversation Turn;
- does not reuse Chat continuation/private provider state;
- uses distinct `InvocationPurpose::Guardian`;
- persists provider intent before provider entry;
- revalidates provider/account/model/destination around extension hooks and dispatch;
- validates the entire verdict before settlement;
- emits no partial verdict.

Extensions receive dedicated `before_guardian / after_guardian` hooks.

## Shared root budget

Guardian review uses the same Phase-43 delegation root as the reviewed team/planner work.

The root additionally pins one `guardian_routing_revision_id`.

Before guardian provider entry:

- the exact source join must still exist and match its digest;
- the root must remain active and before deadline;
- the guardian route/destination must still be valid;
- one shared root model-attempt slot is reserved.

Known provider usage reconciles into the same root token counters. Unknown usage remains unknown and is never treated as zero.

Guardian review consumes no fake child allocation.

## Durable v32 receipts

Schema v32 adds:

- `delegation_roots.guardian_routing_revision_id`;
- `review_operations`;
- `review_human_approvals`;
- `review_release_receipts`.

`review_operations` records:

- exact delegation root and parent Session/branch/turn;
- source kind/id/join digest;
- immutable guardian strategy revision;
- secret-free guardian invocation identity;
- exact input/policy/objective digests and bounded host policy text;
- lifecycle;
- strict verdict + digest;
- bounded completion metadata/error;
- timestamps.

No review table stores full child answers or joined evidence bodies.

Provider lifecycle:

`admitted -> started -> pass | deny | waiting_human | needs_evidence`

Terminal alternatives:

`failed | cancelled | unknown | interrupted`.

A started guardian operation becomes `unknown` on owner restart and is never replayed automatically. An admitted operation becomes `interrupted`.

A settled `waiting_human` approval survives restart because no external provider effect needs replay.

## Human approval

`needs_human` creates one durable waiting approval bound to the exact review/source digest.

CLI:

- `aw review list`
- `aw review show REVIEW_ID`
- `aw review approve REVIEW_ID`
- `aw review deny REVIEW_ID`

Only the stable owning actor may decide it.

Approval is snapshot-bound to the exact reviewed join digest. It does not mutate or reinterpret child answers and does not grant other authority.

A denied human approval can never release the source.

## Release and later continuation

A review release is a separate immutable receipt.

Release requires either:

- guardian verdict `pass`; or
- guardian verdict `needs_human` plus explicit human approval.

Before release, aw reconstructs the exact bounded join from authoritative child Sessions using the same deterministic Phase-46/49 import bounds and verifies the reconstructed join digest against the immutable source receipt.

The root Agent gets a root-only `review_release` tool when guardian review is enabled. Its only model argument is `review_id`.

This permits a later parent turn to continue after an explicit human approval without rerunning the guardian, team, planner, or child providers.

`review_release`:

- works only for the same owning parent Session/branch and exact original parent InvocationIdentity;
- fails closed if the parent provider/account/model identity changed, so human approval never creates a new disclosure destination;
- cannot change policy, source, route, account, model, tools, budgets, or approval;
- creates/reuses the immutable release receipt;
- returns only the verified joined evidence and provenance to the parent Agent.

For immediate guardian `pass`, the team/planner host creates the same release receipt before returning the joined evidence in the original tool call.

## Publication semantics

The parent Agent remains the sole final publisher/synthesizer.

Guardian output is policy metadata, not a substitute final answer and not executable instructions.

For `deny`, `needs_human`, or `require_evidence`, the joined team/planner evidence is not disclosed to the parent model by that tool result.

The parent may see bounded status/reason metadata sufficient to explain the gate.

## Restart / unknown effects

No guardian/provider/team/planner/child effect is replayed from history alone.

On owner restart:

- admitted review operations -> `interrupted`;
- started review operations -> `unknown`;
- settled pass/deny/waiting-human/needs-evidence verdicts remain durable;
- human approvals remain durable;
- release receipts remain durable;
- no guardian provider call is automatically repeated.

A crash after a `pass` but before release may be recovered by deterministic `review_release` without inference.

## Deferred

Phase 50 explicitly defers:

- multiple guardian/reviewer DAG nodes;
- guardian recursion;
- child-to-child/result messaging;
- automatic evidence solicitation after `require_evidence`;
- reviewer-selected providers/routes/tools;
- guardian-granted capabilities;
- parallel planner tasks;
- separate synthesizer models;
- voting/quorum/best-of joins;
- schedules/autonomy/events;
- monetary/cost sub-budgets;
- trusted child shell;
- automatic patch selection/import/merge;
- cross-machine review/child placement.

## Validation requirements

At minimum:

- review evidence/verdict strict parser rejects unknown/malformed/oversized data;
- fixed actor-owned `role=guardian` route required;
- guardian call is tool-free and uses `InvocationPurpose::Guardian`;
- exact source join digest is verified before guardian provider entry;
- guardian attempt consumes one shared root model-attempt/deadline slot;
- guardian attempt consumes no child allocation;
- pass releases exact reconstructed evidence;
- deny releases nothing;
- require_evidence releases nothing;
- needs_human creates one durable approval and releases nothing before approval;
- only owning stable actor may approve/deny;
- approved exact review may release later without any new provider call;
- changed/forged source/review ID is rejected;
- review release reconstructs authoritative child Session prefixes and verifies the original team/planner join digest;
- review tables store no full child/joined answer bodies;
- reviewer pass cannot bypass another missing authority;
- restart after guardian provider intent -> unknown/no replay;
- crash after settled pass can release deterministically without inference;
- v31->v32 migration preserves store identity/restore generation;
- trusted-local direct remains exact-current-schema and therefore requires v32;
- Phase49 and inherited checkers remain green;
- actual-binary smoke proves pass, human-approval/release, deny/no-release and shared root accounting.
