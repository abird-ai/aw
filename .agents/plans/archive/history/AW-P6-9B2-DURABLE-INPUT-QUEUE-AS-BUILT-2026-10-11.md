## 1. Authority, provenance, architectural decisions

1. **Four primitives only:** Runtime, Actor, Message, Envelope; hooks remain only Next/Defer. The queue is a *derived service* over the existing `aw-agent-kernel::message::Mailbox` and original `aw-agent-core::AgentSessionController`. No second Agent, TurnMachine, ToolPolicy, process runner, billing journal, or alternate model executor.
2. **One authoritative SQLite schema v33 and original Session journal:** Queue admission and receipt states are immutable `actor.queue` events appended to the *existing* `audit` and `security_audit_events` under `BEGIN IMMEDIATE`. Source record `actor.input` 9A and `actor.control` 9B1 remain independent factual classes. `runs`, `run_events` and `hazards` remain the only basis for model/tool/effect settlement. No migration, extra SQL table, JSONL format change, version bump, alias, tag, push, remote endpoint, daemon or unapproved grant.
3. **Private encrypted custody, not a shadow authority store:** The existing `LocalSecretStore` encrypts bounded queued UTF-8 bodies with ChaCha20-Poly1305 and private 0600/0700 file/dir enforcement, an owner-only master key and atomic write+sync, using a random write-once `sec_...` blob ID. The SQLite audit records **only** SHA-256, bounded metadata, the encrypted-item reference and immutable receipt states; there is no raw prompt in its audit rows. The existing original TurnJournal still records the real user prompt when the actual Agent Turn starts. No provider-signed private continuation, credential, raw shell command, or arbitrary tool payload is accepted by this queue. A hash may reveal a low-entropy prompt via guessing; hashes are not encryption. Only the trusted Rust `SessionStore` / owner may resolve blob references; `ActorOperationResult::Queue/Queued` exposes a reduced `ActorQueueView` with no secret item references, hashes, process incarnation or message text.
4. **Message identity / authority:** Current Session owner + locally active Workspace writer epoch, bound `ActorKey` generation, current Envelope site, current selected Agent and exact journaled branch are checked at admission. `ActorQueueRequest` carries `(request_id, session_id, branch_id, recipient_site, sender, source sequence/message ID, writer_epoch, Auto|Exact Turn, signed priority)`. 9A Input/9B1 Control/9B2 Queue request IDs share a collision check. `qi_<SHA256(session,queue_request)>` is a reserved, deterministic *correlation* used **only after a current matching Claimed queue fact**; caller-created prefixed 9A Input/queue requests fail. Both the queue and the mailbox enforce monotonic per-sender sequence and do not treat client strings or old Actor keys as a grant.
5. **Bounded queue:** 32 live pending/claimed queue items per `(Session, branch, site)` and maximum 64 KiB UTF-8 text each; signed priority -20..19. Stable original audit enqueue order breaks equal-priority ties. Four consecutive urgent (<0) claims force an eligible normal-priority claim if present, even across owner restart, rather than starvation. Stale absolute Turns block until explicit deletion, never auto-retarget. A persisted `Auto` may use the next valid Turn only under the **same** writer epoch/Session/branch/site and fresh Actor/Envelope/ToolPolicy checks. New writer epoch/failover does not implicitly adopt or reissue old work.
6. **Lifecycle and atomic receipt semantics:** `Pending` means encrypted payload + immutable audit entry exist; it has not run the model. A current owner may `update` (new authenticated encrypted write-once blob + revision CAS, priority only) or `delete` **only while Pending**. `Claimed` means the SQLite writer has atomically reserved one current eligible item and decrypted its verified SHA; a crash here leaves an explicit *Unknown/inspection obligation* (not a replay token). The owner then sends **the same** Actor Input through the current `AgentSessionController`, applying Input hooks and original mailbox grant; 9A `Prepared → Accepted` must commit after `Delivery::Queued`. Queue `Accepted` is a separate writer/process-CAS acknowledgment that validates precisely that immutable 9A Accepted source/target/turn/message ID/digest/priority before committing; it is NEVER model or OS completion. 9A `Accepted → Dispatching` still verifies the *actual* claimed payload before the same original Agent is invoked. Only after the original TurnJournal terminal receipt and hazard checks allow 9A `Settled` does queue `Settled` commit and release private encrypted custody. A dropped paid future keeps 9A claim Unknown and prevents retry/second billable call. No background or on-restart dispatch is installed.
7. **Restart/Unknown, not fantasy exactly-once paid effects:** A pending encrypted item may be rehydrated by an explicitly constructed new owner Runtime/Actor with a NEW generation, but **only the still-current original writer epoch** and same Session/branch/site may claim it. Already `Claimed` or original 9A Accepted/Dispatching cannot be autonomously resent even if no execution receipt was observed; stranded claims must be manually inspected under the current writer. 9B1 Control/9A hazard facts remain independently authoritative; `Inspected` cannot clear them. A settled queue acknowledgment cannot rewrite an uncertain tool/paid receipt. An accepted original Input that was manually inspected must be separately reconciled before retiring its queue receipt. No in-flight Control payload or external Process is replayed after restart.
8. **Crash/custody cleanup limitation (OPEN):** The encrypted file is durably written before the SQLite Pending fact. A process death between these commits can leave an unreferenced encrypted blob; similarly a crash between terminal audit and private unlink may leave retired ciphertext. This does **not** make a runnable queue entry or change the fact ledger, but full orphan-custody garbage collection with proof of unreferenced blobs should be separately designed as an owner-only audited maintenance service before operational retention/erasure guarantees are advertised. Missing `master.key` with existing encrypted items fails closed and never silently creates a new key. `LocalSecretStore` and SQLite are on the same private local filesystem; arbitrary network-mounted/remote storage is not approved.

## 2. Exact implementation ownership

- `crates/aw-store/src/actor_queue.rs` (new): strict `ActorQueueRequest`, `QueueTarget`, `QueueState`, `ActorQueueFact`, private `ClaimedQueueInput`, reduced `ActorQueueView`, deterministic correlation, bounded audit, private custody, writer-CAS enqueue/update/list/claim/ack/finalize/delete/inspect, fairness and restart/Unknown fences.
- `crates/aw-store/src/lib.rs`: exports the typed queue service; no migration or new dependency (existing ring/getrandom/zeroize/sha2/SQLite/SecretStore).
- `crates/aw-store/src/actor_admission.rs` and `actor_control.rs`: cross-class duplicate request IDs/source-sequence fence and reserved queue-derived Input identity checks; original 9A/9B1 audits unchanged.
- `src/actor_owner.rs`: `Service::{enqueue, update_queued, queue_list, queue_fact, admit_next_queued}` and `ActorOperation`'s bounded queue query/list/delete/inspect vocabulary. Full-feature `durable` only. The existing `submit_inner` and `run_once_verified` remain the only actual Runtime Input/Agent execution path. The queue is **not** auto-drained; host explicitly admits one item and runs that one original Turn.
- `crates/aw-store/tests/store.rs` and `src/actor_owner.rs` tests: real isolated private-disk SQLite+encrypted files, read-only projection, corruption/secret loss, writer failover, restart, original-Agent billing/count and queue priority.
