## 1. Binding architecture and limits from original design

The original **2026-10-11** founding contract is authoritative: exactly **four** runtime primitives — **Runtime, Actor, Message, Envelope** — and exactly **two** Hook verbs — **Next, Defer**. ONE original `Agent`, `ToolRegistry`, `ToolPolicy`, `TurnMachine`, immutable `TurnJournal`, single original Session/branch/`WriterEpoch`, original Actor generation, Host SourceKind/id/epoch/effect/site and selected provider account/payer/credential lease. Native SQLite **schema v33**, JSONL **v1**, application **0.15.0**, original E5 C ABI, minimal/stateless and no_std+alloc remain unchanged. No new provider/Tool/OS Process runner, second ledger, new Hook, anonymous process privilege, data migration or generic model `actor_op`. Model-origin self-Current-Turn Cancel/Freeze/Resume, arbitrary OS Process input/signals, child/remote Actor self-Control and human approval remain **DISABLED**. Unknown paid, Tool, OS or future queue effects are NEVER silently retried after interruption; owner/human inspection of hazard facts persists across process restart and snapshot restore. E6 firmware PARKED; numbered Phase69 unauthorized; Phase64/65 indexing/LSP intentionally skipped. Do not claim native Windows/macOS/ARM, release-pinned Rust 1.98.1, paid commercial vendor, hostile-network OIDC/human or natural-power-loss certification from local test artifacts.

### The actual current backup contract, NOT a new one

- Existing `SessionStore::backup(path)` emits **one consistent WAL-aware SQLite `VACUUM INTO` image** with owner-only `0600` custody and fsync of the output and parent directory; AW-P6-10K proved that a rejected create never deletes an existing file. The SQLite backup **does not include** the separate SecretStore master key or items, direct origin execution files, user configuration or external provider resources. Its name and CLI output must not be misinterpreted as a complete credential/queued-input recovery artifact.
- Current `LocalSecretStore` uses **one** owner-only private `secrets/master.key` and write-once authenticated-encrypted items under `secrets/items/sec_<64 hex>.bin`; all master, nonce, ciphertext and tag bytes are sensitive, and a ciphertext's authentication is bound to the exact opaque item reference. Separate files use strict Unix 0700/0600 owner-only mode and no symlink/hardlink aliases. It already handles the key-missing-with-items case; AW-P6-10L additionally refuses a **new unrelated key** when original SQLite audit/credential metadata still references independent encrypted custody.
- Factual original `ToolFinished` output and provider/prompt text in SQLite are **not globally encrypted at rest**. AW-P6-10J permits different model-visible Hook-projected Tool text but preserves original Tool evidence and owner-authorized portable JSONL release. A bundle containing BOTH `master.key` and ciphertext would also be capable of restoring/decrypting original credentials; it is **high-sensitivity owner state**, not a public encrypted portable export or a secure cloud archive merely because a SHA digest accompanies it.
- Current `SessionStore::acquire_local_maintenance_lease("backup", ttl)` fences **original coordinated SQL/execution leases**, and original owner-exclusive `owner.lock` excludes a second ordinary owner Store. Neither is an exclusive lock on *every* public `LocalSecretStore::{put,delete}`. Thus a maintenance lease alone is **NOT proof** of a cross-SQLite/filesystem point-in-time snapshot. Do not ship an apparently COMPLETE composite bundle based on this unsupported assumption.

## 2. Executed native evidence: blocker before implementation

New separate native test file `crates/aw-store/tests/composite_design.rs` deliberately contains **only feasibility and negative-design witnesses**. It does NOT register a new tool, command, operator API, serializable production manifest type or alternate Store engine:

1. `aw_p6_10m_existing_maintenance_lease_does_not_fence_direct_secretstore_mutation`: Opens the real owner-only on-disk SQLite Store and its genuine ChaCha20-Poly1305 `LocalSecretStore`, creates an original encrypted item, acquires an authentic `backup` maintenance lease, and calls original `LocalSecretStore::put` and `LocalSecretStore::delete` **while the lease is active**. Both succeed; the original item disappears and the newly created one decrypts. This **PASSES** as an explicit negative-design observation: **the existing SQL maintenance lease is NOT a file-vault freeze**. No release may describe the current code as cross-resource snapshot-consistent until this has an independently implemented and tested control. This is not a test failure or proof that the original ordinary SQLite backup contract is wrong.
2. `aw_p6_10m_test_only_operator_manifest_rejects_tamper_before_cold_restore`: Builds a real bounded original queued Input and its original encrypted SecretStore item, produces an original `VACUUM INTO` SQLite image, manually copies the matching existing `master.key` and ciphertext into a **test-owned 0700 stage**, writes an actual fsynced owner-only `0600` synthetic `manifest.json`, and verifies exact file allowlist, relative path/no symlink/single hardlink restriction, file lengths/SHA-256, real SQLite `application_id`, `user_version=33`, `store_meta.store_id` and SQLite `PRAGMA quick_check`. The test rejects changed ciphertext, symlink substitution and forged store ID and finally manually assembles a **cold test-only** restored directory and recovers the exact original queued payload via authenticated decryption. This **PASSES** on real SQLite/SecretStore. The toy `DesignManifest` explicitly says `aw-composite-DESIGN-NOT-PRODUCTION`, has exactly one encrypted item, lives **only inside the Rust test target**, and is NOT an authorized stable product format or cryptographic provenance signature. It deliberately does NOT attempt hot backup/restore, cross-process mutation atomicity, a general active-reference traversal, automatic key recovery, owner approval or file erasure.

These are different evidence types: the first proves a **real missing cross-resource freeze**, the second proves owner-file/manifest/recovery **building blocks** can be checked without creating a runnable effect. Neither certifies a new backup command, data retention semantics or an online consistent bundle.

## 3. Selected design: minimum operator-only *cold/quiesced* composite v1, gated for future implementation

**Decision:** An initial production implementation, if separately authorized, should be a *single-owner cold/quiesced, fail-closed snapshot* of an exact original persistent Store—not a hot distributed backup and not an unrelated cloud export. It must use the existing v33 SQLite checkpoint, existing authenticated SecretStore ciphertext, existing process/lease fences, strict private FS custody, and a **new explicit cross-resource quiescence proof**. Any new format is only a *file packaging protocol*, never a fifth Runtime primitive or a provider/Tool execution authority. DO NOT implement or advertise this format in AW-P6-10M.

### 3A. Prerequisite: first establish a real cross-resource mutation barrier

The operator must exclusively own the original Store `owner.lock`, have a current valid original Process/store generation and a valid `backup` maintenance lease, and prove no unclosed original durable execution/Tool/paid attempt is being dispatched. **Additionally, all legitimate first-party SecretStore writers/deleters must honor a common mutation fence across `put`, `write_atomic`, `delete`, provider credential rotation/revoke, queue enqueue/update/delete/claim and extension-secret mutation, including direct locally exported SecretStore handles**. A plain `LocalSecretStore` handle must not bypass it merely because it shares a Unix UID. A lock limited to the SQL connection does not suffice (the first native test confirms this). There must be an explicit writer-drain/owner generation check on both sides and refusal, not waiting indefinitely or silently racing; an uncooperative hostile same-UID root/OS process remains outside the stated local security boundary.

A minimum **cold-only** implementation may alternatively require stopping every cooperating aw process and all explicitly held SecretStore handles before opening the dedicated operator owner; its product/API contract must actually establish this precondition, not merely print advice. An enforced vault gate is preferable. Write-once FS `put` preceding a SQLite audit fact and post-commit blob `delete` may straddle the lease; the final live-reference reconciliation must reject missing active blobs, and never treat orphan files as automatically erasable. Preserve all original `needs_inspection` and uncertain-effects facts, even when backup itself can proceed; backup never means a pending Tool/Process/paid effect is settled.

**Release BLOCKER M1:** No current code proves that a maintenance lease drains/fences every direct SecretStore mutator. The phase-M native test asserts this precise gap. Composite format implementation MUST NOT ship until a future native adversarial test first fails at current behavior and then passes with a real enforced cross-resource gate. Merely adding a `snapshot.json` file and hashing independently captured bytes is a forbidden substitute.

### 3B. Manifest and minimal staging protocol — PROPOSED only

- User explicitly invokes a **trusted original owner-only operator operation** on a real private local filesystem. No model/MCP/extension, browser participant, read-only shared member, or generic remote Actor can request a portable recovery bundle. Do not overload `export_jsonl` with key bytes or silently change `SessionStore::backup(path)` semantics. New public API/CLI spelling requires a separate bounded implementation review; no invented `--backup-all` flag ships in this phase.
- Create a unique unpredictable **0700 private staging directory** under the requested destination's parent using create-new/O_NOFOLLOW and owner validation; never overwrite, follow symlinks, hardlinks, `..` path components or preexisting bundle names. Refuse unsupported filesystems; set explicit **operator-configured finite file-count/size/time budgets** before reading unbounded historical stores. Exceeding limits fails safely; never truncate/downgrade a purported complete backup.
- Under the jointly enforced quiescence barrier, emit WAL-consistent SQLite snapshot using the existing `VACUUM INTO` with original `application_id`, `user_version=33`, `store_id`, original `restore_generation` and a `quick_check`/foreign-key check. Stage the original `master.key` if present and bounded owner-only write-once ciphertext items; never decrypt and serialize credential plaintext into the manifest. Verify exact allowed filenames and permissions, count, length and SHA-256 for every file and **all** staged items. A complete inventory may include extra retired/unreferenced encrypted items, which must not be silently deleted or promoted into active credentials. A separate complete **active-reference** check over the v33 image must verify that every actually Active/Pending encrypted reference in queue/extension/provider/OIDC/OAuth records has a staged corresponding item and decrypts with the staged master/AAD. Historical deleted/retired refs require audit retention, not missing-file rejection. A single `audit` grep or filename count is NOT a substitute for correctly classifying latest immutable state/CAS.
- Proposed strictly versioned **`aw.operator-composite` v1** manifest includes format+version, schema/application/store identity+generation, one SQLite receipt, vault-master receipt (or explicitly never-used absent vault), sorted complete ciphertext file receipt list, capture/validation mode and a `complete` marker. Use per-file size and SHA-256 for **accidental corruption**, not false source authenticity: a malicious same-UID host can forge both files and unkeyed checksums. If network/untrusted media portability or cross-user exchange is later required, design an independently authenticated signing/encryption/key-custody layer; a bundle with its own `master.key` is *not* safe to upload as an encrypted credential archive. Never serialize raw credential plaintext, unredacted logs into the manifest or cached bearer tokens.
- Fsync every snapshot/file and its relevant directories, write the canonical manifest **last** only after all full checks, then atomically rename the complete **staged directory** to a *new* final name on the **same trusted filesystem** and fsync its parent directory. Until the final successful publication, a `.partial` directory is **NOT A BACKUP**. Failure cleanup may touch only the unique staging path created by that run, never existing backups or another caller's symlink or data; crash-left staging is quarantined for explicit operator cleanup, not silently renamed into `complete`. Final release of the mutation fence and maintenance lease follows publication or safe rollback of the staging attempt. No paid/provider/Tool requests are executed to validate a snapshot.

### 3C. Offline restore contract — PROPOSED only

1. Require an **empty owner-only 0700 destination** and explicit operator intent; never replace a live Store or automatically import into another owner's Session. No currently running aw owner, current generation/writer, or retained external handles. A composite backup is a copy of an original security identity, not transferable bearer grants or a semantic `import_jsonl` artifact.
2. Before creating an authoritative new `owner.lock`/starting an Agent, validate manifest format+version, exact normalized paths, unique relative entries, strict mode/ownership/link type, finite budgets and exact lengths+SHA, SQLite quick_check/foreign-key check/application/schema/store ID+generation, and staged key/ciphertext AEAD authentication for every active ref. Missing key with original refs, missing blobs, wrong key, tampering, ambiguous audit status, incomplete manifest, unfamiliar schema, extra symlink/hardlink, or a final `complete` name without valid receipts MUST fail closed without modifying the destination or minting a new key. A successful manifest checksum does **not** prove a commercial paid-provider invoice or hostile operator identity.
3. Stage the verified image in a *new* owner-private directory, then atomically publish only after all referential checks pass. On first real `SessionStore::open`, existing process/restore generation fencing and original `TurnJournal` recovery must revalidate original unsettled writes/hazards: never dispatch queued work, Tool effects, interrupted paid provider calls, or model-proposed Process commands as a side effect of restoring. Do not fabricate a new WriterEpoch/Actor generation as permission; the new owner obtains independently authenticated authority, and old in-flight leases are fenced.
4. Restore behavior with a mismatched store identity is **reject**, not accidental cross-owner import or key rotation. Wrong-master `ChaCha20-Poly1305` AAD authentication failure rejects active encrypted custody. Unknown blob refs and uncommitted pre-audit orphans are NOT deleted automatically. Preserve previous backup; no operator UI may report a completed restore before original SQLite/vault integrity and receipt/hazard checks return success.

## 6. Rejected alternatives, open research and next implementation instructions

**Rejected as unsound now:** treating existing maintenance lease as a vault-write lock; copying live `sessions.sqlite3` without its WAL-aware `VACUUM INTO`; copying master/key without strict owner/manifest/custody checks; listing arbitrary files into a JSON manifest without a stable SQL+vault cut; re-keying ciphertext on restore with a fabricated master; assuming checksums sign authorship; embedding real generic Tool output and master key in unauthenticated public or model-visible export; deleting orphan ciphertext or unknown paid effects during backup; enabling model-origin arbitrary Process/Actor/Human operations to run recovery. Never broaden `SessionStore::backup(path)` silently: its existing SQLite-only semantics are used by the original CLI/SDK and remain documented. No general object-storage driver, new schema v34, archive password/key service, generic Tool-output encryption, E6 or Phase69 is authorized by AW-P6-10M.

**Remaining OPEN:** real inter-resource quiescence/fence; complete active-refs inventory and caps; actual operator manifest/library API; stage-and-publish fsync/rename; standalone transactional cold restore; ciphertext/key lifecycle, rotation/erasure and cloud encryption; arbitrary natural power-loss, actual native Windows/macOS/ARM, pinned release Rust 1.98.1 (current local Rust 1.95.0), live commercial billing/recovery, independently authenticated human OIDC/guardian and external penetration/security certification. Whole-repo `cargo fmt --check` has known historical unrelated drift; format only newly owned Rust and use `git diff --check`. No push, tag, release.

**Candidate AW-P6-10N (separately authorized implementation):** start with a real original SecretStore mutation barrier across *all* writers/erasers, test it negative-first, and wire it into the original owner+maintenance fence. Only when native races close, incrementally add operator-only cold stage/manifest/validate/atomic-publish and cold restore in bounded cuts, with no new provider/Tool engine, no silent retry and no broader model permissions. Preserve all historical as-builts and the independently owned UX path, and use exact-owned-file atomic Git index/CAS commits.
