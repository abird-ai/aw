## 2. Negative-first bug reproduced: rejected backup DELETED an existing private snapshot

The existing original `SessionStore::backup(destination)` in `crates/aw-store/src/lib.rs` acquires the original current authoritative maintenance lease, calls exclusive `private_new(destination)` (Unix `O_NOFOLLOW|O_CLOEXEC|O_EXCL`, mode `0600`, verified owner, non-link), then uses SQLite `VACUUM INTO` for a consistent current WAL-aware snapshot. **BUG:** If `private_new` failed because `destination` ALREADY EXISTED, the error cleanup unconditionally called `fs::remove_file(destination)` regardless of who created the file. A perfectly ordinary retry at the same backup path silently DESTROYED the PREVIOUS actual SQLite backup. The same dangerous cleanup could remove an unrelated existing owner-only file or preexisting symlink. Failure to overwrite was therefore not non-destructive, contrary to the existing CLI/STATE.md new-private-path contract.

**Concrete native regression written BEFORE implementation:** `aw_p6_10k_rejected_backup_cannot_unlink_existing_original_private_data` in `crates/aw-store/tests/store.rs` creates an original private on-disk state, makes an actual valid nonempty SQLite `VACUUM INTO` snapshot, confirms `0600`, then asks for the same snapshot path again. The original code **FAILED the new assertion** because the previous snapshot file was gone (`ENOENT`); the test also explicitly covers a distinct preexisting private data file and a preexisting symbolic link to the valid snapshot. This is a reproduced actual data-loss hazard, not a speculative privacy concern or a claim of external malice.

## 3. Minimal single-function source correction and conservative crash durability

**Only production code touched:** `crates/aw-store/src/lib.rs::SessionStore::backup`. One local `created_by_this_backup` flag becomes true **only after** `private_new(destination)` succeeded in exclusive creation. Error cleanup may unlink **only** that request's newly created failed snapshot, never an existing backup/private file/symlink for which creation returned an error. Original `VACUUM INTO`/maintenance lease/SQLite source and no-overwrite path semantics remain, no public API/signature change or schema/format migration. The code still propagates the primary SQLite/path/file error, releases the original lease as before and does not rewrite an already successful backup. It does not invent a generic `BackupManager` or new detached service.

For a **successful** new snapshot, the code now reopens the resulting SQLite file through the existing platform `aw_platform::open_private_existing` owner-only/no-symlink single-link validator, explicitly `sync_all()`s the output and `sync_parent()`s its directory **before reporting success**. This addresses SQLite `VACUUM INTO`'s lack of an automatic fsync promise for the produced file and keeps the private file-mode guard. A failed sync triggers cleanup **only** if this request created that file. The existing backup is a consistent SQLite snapshot, **not** an encrypted collection of all external credential/SecretStore file trees and NOT a guarantee of crash-atomic creation from its first byte. A process crash before success may leave an incomplete newly created snapshot; the caller must use unique backup names and inspect/verify backups. No fabricated return value implies remote durability, power-loss resistance on every filesystem, portable access without secrets, or owner-independent cross-user privacy.

## 6. Still OPEN — at-rest confidentiality, retention, hostile-process and release guarantees

1. **Generic Tool output confidentiality:** Authenticated encryption/erasure of raw original `ToolRecord` / `run_events` / `nodes` contents, log/backup/export retention and cryptographic user key custody is NOT implemented here. The existing SQLite `VACUUM INTO` backup may contain raw plaintext Tool responses (the explicit new test proves it), owner-approved JSONL export intentionally includes saved Tool text, and a copied file must be treated as **sensitive private user state**. Existing `SecretStore` ciphertext protects its own secret references only; a SQLite-only backup is not automatically a recoverable backup of separate SecretStore encrypted blobs/master key. A real all-Tool private-at-rest design needs independent owners/keys, recovery/rotation, cross-platform support, original immutable receipt hashing, durable staged transition, restore/erasure semantics and explicit approval before changing schema/ABI or export policy.
2. **Backup durability:** Output file and directory fsync are now explicitly requested before success on supported Unix host filesystems. This does not prove natural power-loss/fsync reordering, atomic visible naming from the first byte, distributed/remote object-store durability, or a safe preemptive same-UID attacker replacing an output path in a hostile writable directory. Existing `private_new`/`open_private_existing` platforms verify 0600/no-follow/single link; a malicious same-UID root/kernel host remains outside security certification. Existing output names must be unique; a crash may leave an incomplete new snapshot that requires inspection rather than automatic deletion of other files.
3. **Authorization:** Backup is a trusted local `SessionStore` management method and should only be invoked by the original authenticated owner operator. It does not add browser, model, MCP/extension or guest backup permissions. Export has an original owner-only check and separate cross-owner release constraint; portable JSONL includes sensitive normal prompt/Tool content by design, is not encrypted or cryptographically signed merely because it has a SHA checksum.
