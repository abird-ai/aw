## 1. Exact model-origin Write permission without a new execution system

- **Host-only explicit installation:** `aw::model_effects::install_queue_enqueue(&Service,&mut Agent)` requires the **same currently authenticated original** `actor_owner::Service` and journaled Agent. The original live Actor's **pre-existing** `Envelope` must ALREADY contain `ExactGrant {name:"queue_enqueue", kind:Host, source:"trusted-host", source_epoch:1, effect:Write}`. The host cannot create a new grant at this API, and an existing Host/Read grant, wrong source kind, mismatched epoch, or a model-requested Tool name is insufficient. The tool is installed via the **original `Agent::register_host_tool`** and the matching original `ToolPolicy::permit_source` Write, with the original `ToolRegistry`, provider model proposals, schema validation, exact source/effect/site admission, mandatory AgentStepGate safe points and original ToolStarted/ToolFinished journal. The existing D1 `agent`/`queue`/`process` observation-only Tools are unchanged and remain independently granted. No tool installs by default in ordinary CLI/R12/TUI/web/signed AwNet, and enabling the Write name is an affirmative trusted host decision, not an inferred project/Prompt/Plugin grant.
- **Tiny exact model input:** Named tool **`queue_enqueue`**, declared `ToolEffect::Write`, accepts **only** `{"op":"enqueue","text":"bounded UTF-8"}` with exactly those two keys. `text` must be 1–4096 bytes, have no NUL/terminal controls other than newline/tab, and pass the existing strict ToolCall schema and host semantic validation. Provider arguments cannot supply `ActorKey`, principal, site, writer epoch, message ID, sender/source sequence, priority, target Actor, specific recipient Session/branch, process ID, administrative grant, approval, source or a network endpoint. Target is fixed **`Auto`**, normal priority `0`, same original owning Session/branch/recipient execution site. The tool may only **create a future encrypted Pending Input**; it cannot claim/drain it, dispatch another provider, wake a daemon, mutate another pending user Input, or approve an external effect.
- **Exactly once per originating real journaled Turn:** `Service::enqueue_model_future_text(&ToolContext,text)` checks the existing D1 original authorization *again*—current live nonterminal Runtime Actor generation, exact principal, original active `ToolContext` account/payer/credential, current writer epoch+site and Session+branch, uncancelled positive original Turn, original immutable `actor.input` **Dispatching** fact and actual matching active Runtime Input. It independently rechecks the *Write* source/epoch/effect grant at the same point. The request ID is **host-generated deterministically** as `mq_` + SHA256(domain-separated original Session ID, branch ID, originating Turn ID). It is deliberately independent of model-proposed ToolCall ID, text, prompt, external retries and process generation: two proposals or an interrupted retry originating from the same Turn must collide **forever**, even with different text. At most ONE future Input per originating Turn can be accepted. An agent may create another queue Input only through a genuinely new independently journaled Turn with a new positive Turn ID.
- **Original writer chooses source sequence atomically:** `aw-store::SessionStore::actor_queue_enqueue_minted` is a small strictly host/service path through the **existing** `actor_queue_enqueue_inner` and same private encrypted SecretStore. Caller MUST pass `message_id:0`; the original SQLite `BEGIN IMMEDIATE` transaction checks the complete immutable original Input/Control/Queue/Notify sender sequence history, reserves all future closure audit capacity, enforces 32 Pending/Claimed per receiver and all exact Session owner/branch/current WriterEpoch fences, and mints `max_historical_sender_sequence + 1` *inside the same transaction*. Explicit ordinary `actor_queue_enqueue` stays unchanged and still rejects caller-supplied stale/nonmonotonic sequence. Duplicate request-ID collisions occur **before** creating the immutable Pending fact and any duplicate new encrypted blob is cleaned best-effort. Overflow/foreign writer/source/duplicate request, wrong author or stale epoch fail closed. No table or source sequence API is exposed over R12/web/remote/model JSON.
- **Real original receipts / no retry:** The original Tool is a **Write effect**, not disguised as Read. The Agent journals its full ToolCall proposal and tool-result/Write hazard using its preexisting intent/receipt semantics; only the queue's immutable SQLite `actor.queue` **Pending** fact establishes encrypted future queue acceptance, **not** a billed model execution or a future Turn settlement. A future invocation enters the model ONLY after an explicit current owner call `Service::admit_next_queued(&Agent)` and `Service::run_once(&mut Agent)`, which uses original 9A/9B claims, journal and safety checks. No automatic recursion, replay after SIGKILL or uncertain Tool/Control failure, or new background scheduler. The accepted metadata tool output includes only opaque deterministic request ID/state/revision, `NOT_DISPATCHED`, `NEVER_AUTOMATIC`, target Auto, normal priority; never plaintext future text, AES/ChaCha ciphertext ref or raw SHA.
- **Important confidentiality boundary:** The **queue-specific audit** contains only existing SHA256 and encrypted opaque blob references; on-disk `LocalSecretStore` holds ChaCha20-Poly1305 ciphertext. However, **original model-generated ToolCall arguments (including requested future text) are legitimately recorded in the original Agent's immutable journal** as provider proposal evidence. D2A does NOT claim that the text is absent from *all* SQLite data or from the original model context. The destination queue still avoids plaintext in its *own audit*, and metadata read queries remain redacted. In the deliberate duplicate-Write case, the first queue fact is Pending and only one encrypted blob is accepted, but the original Agent may mark the originating Turn **Unknown/needs inspection** rather than fabricate a settled Tool batch because the second Write conflicted. Even an explicit owner claim must fail until the original hazard is reconciled through the existing native policy.
