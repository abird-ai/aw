## 2. Concrete negative-first defect: a rewritten file AND checksum fooled original staged verification

At the beginning of Q, `PartialCapture::verify` checked only the SHA-256+size from its own *untrusted* `manifest.partial.json` against the corresponding file bytes, plus SQLite `quick_check`/`application_id`/`user_version`/`store_id` and physical file-count metadata. This detects accidental post-capture corruption but DOES NOT authenticate copied `master.key` or private ciphertext to the original SQLite active-ref ledger. An operator-local staging tool or compromised copied filesystem capable of rewriting both file bytes and the unkeyed manifest hash could replace a staged ciphertext or stage a wrong 32-byte master key and still have the old `verify()` return success. There was no public restore execution path or actual paid vendor vulnerability demonstrated, but the private semantic verification boundary was incomplete.

**Genuine negative-first native regression:** Added `aw_p6_10q_rehashed_tampered_active_ciphertext_cannot_pass_standalone_verification` and `aw_p6_10q_rehashed_mismatched_master_cannot_pass_standalone_verification` to the existing private Rust module's tests BEFORE modifying production verification. Both created a genuine P staged SQL+key+Queue item, corrupted only the staged ciphertext or replaced the staged master, recomputed the corresponding file receipt SHA-256 and wrote back a well-shaped private manifest. Both **FAILED their new denial assertions against old P code**: the old private verifier incorrectly accepted the rehashed but unauthenticated data. After Q, both **PASS** with active-ref AEAD failure, never executing provider, Tool or Queue work.

A separate SQL test originally tried to mutate an immutable `audit` row on the staged copy. The original SQLite immutable-update trigger correctly rejected that attempt *before* the staged verifier could be tested; this was **not** counted as a reproduced verifier failure. The native Q test thereafter drops that trigger **ONLY inside the synthetic staged test copy**, simulating an offline whole-file rewrite by a local operator, updates one Queue `payload_sha256` row and recomputes the staged SQLite manifest hash. The new source-independent verification still rejects the changed Queue body digest despite internally consistent file hashes and structurally valid SQLite. No original source/production SQL trigger is disabled or modified.

## 6. Publication boundary preparation (DESIGN, not a shipped feature)

The standalone verifier now supplies a bounded, read-only source-independent prerequisite for later operator publication. It **DOES NOT** authorize changing `PartialManifest.complete` to true or renaming the current `.partial` into a final archive. A separately reviewed Q-successor implementation needs:

1. An explicit original authenticated owner-only operator API (NEVER model/MCP/extension/Web/remote grants), exact backend generation/maintenance/active-custody and private destination validation. Avoid changing the existing SQLite-only `SessionStore::backup(path)` or JSONL export behavior.
2. A separately versioned, stabilized complete-format manifest and complete inventory (SQLite, original master where applicable, all retained ciphertext, original active refs, bounded file count/bytes, unencrypted factual ToolOutput privacy limitations). Strong replay/hazard and original source authenticity caveats. No copied key+items to public cloud without independent authorized archive encryption and key custody.
3. Publish only after fully verified source-independent image, staged file/dir fsync, a true **same-filesystem, no-overwrite atomic directory rename** plus parent fsync and a stable completed manifest. Before the successful final rename, a `.partial`/failed/quarantined stage is NEVER considered a valid backup. Protect previous user backups and owner data from all error cleanup, cross-mount moves, symlinks, crash-foreign partials and attempts to import another Store identity.
4. Independent native fault tests at pre-copy, between-files, after-private-manifest, pre/after-rename and parent-fsync boundaries, including real separate process exit and later actual natural power-loss only where feasible; verify prior backup preservation and that unfinished stage is never published. The current two actual child-exit tests cover only a subset; no power-loss/fsync reorder or cross-platform guarantee is claimed.
5. **Offline restore remains separately gated**: real source-independent re-authentication of original SQLite/store generation, active refs, original AEAD/Queue body digest, correct original actor/process WriterEpoch fencing and immutable hazard/no-paid/Tool/OS replay, on empty owner-only destination, before activating an Agent.
