## Proven bug and minimum fail-closed correction

**AW-P6-10-F1 — missing coordinated Process incarnation could masquerade as same owner.** `SessionStore::in_memory()` intentionally has `process_identity()==None`, but the new model-origin OS-Process `model_process_prepare` previously accepted it and recorded an immutable `Prepared` effect with both `owner_process_id=None` and `owner_store_generation=None`. `model_process_transition` compared `None==None`, potentially permitting an `Applied` OS effect receipt with NO verifiable original executing Process incarnation. This was a factual external-effect authorization bug, not only documentation drift.

1. Introduced native negative regression `aw_p6_10_model_process_requires_real_process_incarnation_for_effect_receipts` in `crates/aw-store/tests/store.rs`: build a real in-memory SQLite Session/WriterEpoch/Input Dispatching/original started Turn and demonstrate the Store must reject an externally effectful model Process intent. **Before the fix the regression FAILED** on its prepared-intent assertion, confirming the issue, not guessing from source.
2. Both prepare and terminal transitions now require the existing `SessionStore::coordinated_process()` concrete current owner identity in `crates/aw-store/src/model_process.rs`. Prepared always pins `Some(process_id)` and `Some(store_generation)`; receipt only succeeds against the same current Some incarnation and existing exact writer/request/audit checks. `None` is **never** affirmative evidence of Process custody. This reuses the one coordination authority; no new actor/policy/process lifecycle or compatibility branch.
3. **After the fix:** new negative regression 1/1, earlier seven focused Process/restart/future-pause tests 7/7, and whole original Store/CLI/Process suites below PASS. Actual persistent current-owner Store behavior and exact Process Tool grant/effect distinctions are unchanged. No SQLite migration, JSONL/C ABI modification, automatic replay or broadening of model authority.
