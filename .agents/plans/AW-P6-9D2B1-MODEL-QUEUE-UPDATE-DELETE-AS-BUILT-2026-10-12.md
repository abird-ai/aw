## 1. Exact four-primitives / two-hooks architecture

There are still precisely four primitives **Runtime, Actor, Message, Envelope**, two Hook verbs **Next, Defer**, one original `Agent`, `ToolRegistry`, `ToolPolicy`, `TurnMachine`, original journal and writer-fenced SQLite v33 queue and SecretStore. This is a small derived service on the existing 9B2A encrypted `actor.queue` and 9D2A model-origin `queue_enqueue`, **not** a new executor/queue/table, generic model `actor_op` passthrough, provider payment loop or a new default tool set.

**D2B1 implements only bounded `queue_update` and `queue_delete` for previously model-created, unclaimed, Pending future Inputs.** Neither is installed automatically in CLI/RPC/TUI/web/MachineLink; both are explicit trusted-host Rust SDK registrations on the **same** already journaled Agent. They have **different names and independently pre-minted Host/trusted-host/epoch1/**`Write`** Actor Envelope `ExactGrant`s and the same original ToolPolicy exact Host/Write source/site/cap checks. An existing `queue_enqueue` Write grant or D1 queue Read grant does **not** authorize update/delete. `aw::model_effects::install_queue_dispositions(&Service,&mut Agent,&BTreeSet<DispositionTool>)` verifies the original active owner/writer/Agent and all requested exact Envelope grants before registering any source into its one original ToolRegistry, with rollback on failure. No authority comes from a model ToolCall name, provider schema, project markdown, ToolContext JSON or external untrusted source.

## 2. Precise typed model operations and custody

| Tool | Model-supplied JSON | Original `ToolEffect` | Allowed result |
| --- | --- | --- | --- |
| `queue_update` | `{ "op":"update", "request_id":"mq_<64 lowercase hex>", "expected_revision":N, "text":"new UTF-8" }` | **Write** | **Existing** Pending model queue item's encrypted body is atomically replaced with fresh write-once ciphertext; original sender, recipient site/branch, priority, message sequence and Auto target unchanged; next revision returned |
| `queue_delete` | `{ "op":"delete", "request_id":"mq_<64 lowercase hex>", "expected_revision":N }` | **Write** | The existing, still Pending model-owned queue item is terminally marked Deleted, revision advanced, and the retired ciphertext unlinked **after** durable commit; no future model/Tool execution |

All JSON keys are exact and extra fields fail. The model cannot choose an ActorKey, target principal/site, provider/account, process handle, user approval, writer epoch, source sequence, priority, destination, tool grant or other model operation. Update text is 1–4096 bytes and rejects NUL/terminal controls aside from newline/tab. The model must provide a **positive exact target revision**, checked by the existing SQLite writer CAS in `BEGIN IMMEDIATE`. Delete never accepts replacement text. A claimed, accepted, settled or otherwise retired item cannot be changed. An ordinary user-created Input cannot be modified, even if the model knows its request ID.

**`mq_` is not sufficient authority:** The new shared `aw_store::model_queue_request_id(session,branch,turn)` retains exactly the 9D2A domain-separated SHA256 ID algorithm. Under the SAME SQLite transaction, D2B1 verifies that a target `mq_` ID corresponds to an **earlier factually Settled original `actor.input` Turn** for the same Session, branch and exact Actor sender, and that the existing queue fact's sender/recipient site/branch/positive revision and Pending state match the live owner. A spoofed `mq_` entry without such a previous real settled journal/Turn is explicitly denied. This is deliberately stronger than a prefix check. A previous Actor generation/cross-site source has no inherited model write authority.

**Once per originating Turn across both operations:** The current real `ToolContext` is checked by the existing D1 `Service::verify_model_observation` against the original immutable **currently Dispatching** Input, matching actual Runtime active Turn, owner Session/branch/site/writer epoch/Actor generation, uncancelled call and selected provider/payer/credential identity. It independently checks exactly the selected `queue_update` or `queue_delete` Host/**Write** grant. `Service::dispose_model_queue` then mints `md_` + SHA256(domain-separated Session+branch+originating Turn). The original queue Store now appends **one immutable `actor.model.queue_disposition` action** (no new SQL table) in the **same `BEGIN IMMEDIATE` transaction** as the queue's next `actor.queue` fact. That dedicated marker records only the bounded typed original current-Input/Turn correlation, action/target/revisions/state, **never private text**. A second update or delete from the same original Turn, even with a different ToolCall ID, target or text, collides with the immutable marker and can never commit another disposition or silently replay after a crash/restart. This marker does not artificially count as an original Agent payment/Turn settlement.

For update, the existing private `LocalSecretStore` writes and fsyncs a fresh ChaCha20-Poly1305 blob **before** the queue/marker transaction, then unlinks the superseded ref only **after** committing both facts. For delete the same atomic queue/marker commit precedes unlink. A pre-commit failed attempt cleans only its own fresh ref best-effort. Any crash or error **after** commitment but before retired-blob unlink is an uncertain Tool result, not permission to repeat the model mutation; the original 9B2B ledger-proven retired-only custody sweep can later remove provably stale blobs without touching unrelated provider credentials. Unreferenced pre-ledger orphan ciphertext and physical forensic erasure are not claimed solved.

**Honest private-content boundary:** Neither the `actor.queue` audit nor `actor.model.queue_disposition` audit nor a model-facing ToolOutput carries replacement plaintext or ciphertext file refs. Original model proposal arguments **do** enter the original Agent's immutable ToolCall journal as evidence; do not claim entire SQLite is plaintext-free. The future revised text becomes a model prompt **only** after a separate explicit current owner `admit_next_queued`/original `run_once`, never by model-origin update itself. `queue_delete` stops that future dispatch entirely. Duplicate Update+Delete proposals in one model tool wave may leave one committed disposition and an original **Unknown/inspection-required** Tool/Turn hazard; the owner must not claim the queue or repeat a paid attempt until separately reconciled. This is the existing Agent journal's no-replay guarantee, not a new executor.
