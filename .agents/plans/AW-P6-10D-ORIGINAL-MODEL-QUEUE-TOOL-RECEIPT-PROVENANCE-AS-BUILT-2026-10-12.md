## 1. Exact architecture and previously established authority

The 2026-10-11 AW-P6 founding contract is normative: exactly **Runtime, Actor, Message, Envelope** four primitives and **Next, Defer** two Hook verbs, a single original `Agent`, `ToolPolicy`, `ToolRegistry`, `TurnMachine`, original mandatory immutable `TurnJournal`, SQLite **v33** and JSONL **v1**, C ABI E5 and application version **0.15.0**. One original owning WriterEpoch/Session/branch/Actor generation/verified execution site/selected payer/credential ToolContext controls paid Turn and Tool effects. Existing `queue_enqueue`, `queue_update` and `queue_delete` original model Tools remain separate **explicit Host/trusted-host/source epoch 1/Write** grants, OFF by default in CLI/R12 RPC/TUI/Web/QUIC. A ToolCall name, ActorKey, `mq_`/`md_` hash, MCP hint, inherited source or status UI text is NEVER an authorization. Model self-current cancellation/freeze, child/remote Actor control, arbitrary OS Process signals/stdin and model-origin *human* guardian approval remain DISABLED. An accepted encrypted future Pending queue item is not a paid execution, dispatched Turn, or Tool receipt. Unknown/cancelled/ambiguous original provider, Tool or OS effects are never automatically replayed.

**This wave changes ONLY the original host model queue Update/Delete eligibility predicate.** Existing original D2A future `queue_enqueue` writes ONE encrypted Pending `mq_` item to the original SQLite `actor.queue` audit and original `LocalSecretStore` in an already journaled current Turn. Existing D2B1 later allows a separate model-origin `queue_update` or `queue_delete` for that exact earlier Pending item under a distinctly granted current Write Tool, one original `md_` immutable disposition marker, revision CAS and no automatic next Turn. AW-P6-10C already proved canonical hash `md_` and `mp_` IDs. However D2B1's Store gate had inferred “model-owned” only from the *earlier factually Settled Input/Turn*, same original sender/branch/site and deterministic `mq_` ID. A direct trusted Host `SessionStore::actor_queue_enqueue_minted` can create that same `mq_` without any model `queue_enqueue` proposal or original ToolStarted/ToolFinished, so the lower Store was potentially treating host-queued work as model-owned. Correct original owner/WriterEpoch/Turn gates prevented unauthenticated external actions, but the missing **Tool ancestry** was a real reduction in the intended model target-custody restriction.

## 3. Implemented minimal derived service over the original immutable Journal

**Owned production source:** ONLY `crates/aw-store/src/actor_queue.rs` adds the bounded private `SessionStore::original_model_enqueue_receipt()` gate within `actor_queue_model_disposition`. It reuses already persisted `runs` and `run_events`, **no new tables, sidecar provenance tokens, optional Hook, ABI/schema/JSONL change, other Agent model loop, Process executor or alternate journal**. It reads real original Journal entries in the very SAME existing SQLite `BEGIN IMMEDIATE` transaction as the requested queue Update/Delete and shared `md_` marker, before committing any new private ciphertext reference or queue state. Its first-party original `TurnJournal::append` invariants already require Assistant proposal→ToolStarted→matching ToolFinished, so the new lower service additionally checks precise content/status and output correlation:

1. Original Input `Settled`, earlier Turn, exact same Session/branch/Actor-sender and deterministic `mq_` target. Original `runs` has **exactly one `status='completed'`, `attach_status='attached'`** original run for that Session/branch/Turn and the original **enqueue-time writer epoch** (not the current later owner epoch). The stored original `InvocationIdentity.actor` must equal the original current Session owner, and a journaled `InvocationStarted` plus factual `InvocationFinished` with `response_received`/non-null metadata must precede the bounded original `Assistant` proposal. No replay from a recovered `interrupted` or unattached run.
2. The single original journal's Assistant `queue_enqueue` ToolCall is validated as the same call that the original ToolStarted/ToolFinished refers to. An independently journaled, host-authorized `ToolRevised` is supported only with original `Host/trusted-host/epoch1/Write` provenance and unchanged call ID/name; the actual execution's exact arguments are checked. ToolStarted must have `ToolEffect::Write`, `ToolStatus::Running` and exact original enqueue execution **site**. Its strict `{op:"enqueue",text:"…"}` text must SHA256-equal the **FIRST immutable Pending queue payload digest** (not the latest owner-edited ciphertext). The first queue item must also have original Auto target and priority0, site/sender/sequence, revision1. The Tool's proposal text is read from existing private journal only during the proof; it is never recopied into queue/disposition audit or model-visible observer data.
3. The original correlated ToolFinished must match the same call ID, arguments, original Write effect/site, and be **Succeeded**, with non-error, non-truncated original ToolOutput. Bounded parsed factual metadata must name the exact expected `queued_future_input`, the actual `mq_` request ID, Pending, revision1, Auto target, priority0, `execution:NOT_DISPATCHED` and `retry:NEVER_AUTOMATIC`. Two matching receipts or any incomplete/missing/mismatched set **cannot** establish origin. Original `run_events` count remains bounded by the existing 512-event Journal limit; this one read is inside the original writer transaction and is independent of optional presentation hooks.
4. Only AFTER all original immutable proof checks does existing D2B1 append the next `actor.queue` fact AND the once-per-current-Turn `actor.model.queue_disposition` in the same transaction. Every other existing exact owner/source/effect/site/WriterEpoch, encrypted Pending CAS, ciphertext safe unlink, post-commit Unknown, and no auto-replay rule remains. The new gate never executes a provider, tool, Process, remote call, or queued Input. Host-only edits of a legitimate item's **later** Pending text and priority remain valid: their latest encrypted body/priority can differ from the original model Tool proposal without erasing the original immutable creation evidence.

**Existing trust limitation, not hidden:** Current original `ToolRecord` has call, declared effect, execution site, status and output, but not a separate cryptographic ToolSource epoch attestation on every entry. Actual original `Agent`+`ToolPolicy`+`Envelope` rechecked exact Host grants before the Tool ran; this SQLite inspection does NOT independently certify a malicious current same-UID Rust host that can forge a new original Journal itself. No source-only checksum or local fake provider certifies a commercial model's identity/charges. Adding an independent provider-signed origin or external human identity would be a different authorization/data design and is NOT claimed here.
